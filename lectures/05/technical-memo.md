## 3. 宿題（実装）：検索結果に前後 1 ページの本文を付ける

### 3.1 変更したコード

| ファイル | 変更 |
|---|---|
| `app/config.py` | `RAG_NEIGHBOR_PAGES = int(os.getenv("AIE_RAG_NEIGHBORS", "0"))` を足した。既定の 0 は配布版と同じ動き |
| `app/retrieval.py` | `search()` を `vector_search()`（ベクトル検索だけ）と `add_neighbors()`（前後ページを足す）に分けた。`search()` は、`RAG_NEIGHBOR_PAGES > 0` のときだけ前後を足す。`python -m app.retrieval` の表示に「前後ページ：〜の隣として追加」を出す |
| `app/retrieval.py` の `search_graph()` | 入口（seeds）を `vector_search()` から取るように変えた。前後ページを有効にしたとき、Graph の入口に隣のページが紛れ込まないようにするため |
| `tests/test_retrieval_neighbors.py` | 前後ページの付き方のテストを足した（下記） |

ツールの docstring と指示文は変えていません。比べる条件を、取得処理の 1 か所だけにするためです。足したページには `"source": "neighbor"` と `"neighbor_of": <どの検索結果の隣か>` を付けました。モデルは、この 2 つのフィールドで、検索で見つかったページか隣のページかを見分けられます。

`add_neighbors()` の規則（課題資料の「別の資料をまたがず、同じページが重複しないようにします」に合わせた）：

- 前後のページは、**同じ `document_id` の中だけ**で探します。第2回の p.1 の前に、第1回の最後のページを付けることはありません
- すでに入っているページは足しません。検索結果どうしが隣り合う場合も、2 つの検索結果に共通の隣がある場合も同じです
- 検索結果の順位と件数（`RAG_TOP_K`）は変えません。各検索結果の直後に、前のページ、後ろのページの順で並べます

テスト（6 件）で確かめたこと：前後ページの付き方と付けた理由の記録、資料をまたがないこと、重複しないこと（共通の隣・隣り合うヒット）、`width=2` のときの順番、既定（0）では配布版と同じ結果になること。もう 1 件、前後を「ページ番号 ±1」で探すために、**対象資料のページ番号が連番であること**も実データで確かめています。

### 4.2 設計：データの形・持ち方・検索方法と、選んだ理由

**方式**：ベクトル検索で入口のページを見つけ、その本文と一緒に、**そのページがある章の目次**を返します。モデルは目次を見て、足りないページだけ本文を読みます。

**データの形と持ち方**：新しい索引は作りません。今ある 2 つをそのまま使います。

- `data/rag_data/index.sqlite3`：入口を探すベクトル検索（配布版と同じ）
- `data/rag_data/tree.json`：講義 → 章 → ページの階層。ページ ID から親の章を引けるように、実行時に「ページ → 章」の対応表を作ります

**選んだ理由**（演習と基礎・実装の結果から）

| 方式 | 演習・宿題で見えた弱点 |
|---|---|
| 基本 RAG | 上位 K 件しか見えない。章全体を問う質問では、何度も検索し直して重くなる（4.4） |
| Tree | 最初に章を当てる必要がある。根拠が別の章にあると外す（演習 Q2 の p.13）。応答回数が多い |
| Graph | 毎回、最大 10 ページの全文を返すので重い |
| 前後ページ（実装） | 近くの漏れしか補えず、K=5 では費用だけ増えた |

目次付き検索なら、入口探しはベクトル検索に任せられます（章を当てなくてよい）。そのうえで、章の残りのページはタイトル（と先頭文）だけの安い形で見せ、本文が要るページだけを読めます。

### 4.5 自分の用途に採用するか

- **採用する場面**：講義資料の Q&A で、「この章で何を扱ったか」「この回の構成は」のように、まとまった範囲を問う質問がある場合。基本 RAG はこの種の質問で、検索を繰り返して重くなり、しかも答えが欠けました
- **採用しない場面**：1 ページで答えが決まる質問（Q1）や、資料にない質問（Q3）。基本 RAG の方が安く、答えは同じです。章をまたぐ列挙（Q5）も、基本 RAG の方が軽いです
- 実際に使うなら、質問の種類で方式を切り替えるのがよいと考えます。たとえば、エージェントに `search_materials` と `search_chapters` の両方を渡して選ばせる方法があります。ただし、モデルが道具を選び間違えると、v1 のように無駄な呼び出しが増えるおそれがあります（未検証）
- 比較の限界：各 2 回だけで、モデルは 1 つ（flash-lite）、狙いの質問は 3 つです。v2・v3 の改良は、同じ質問を見ながら行ったので、**この質問に合わせ込んだ可能性**があります。別の章を問う質問で確かめたのは Q7 だけです

## 6. このあと気をつけること

- 実験に使う費用は、キャッシュの有無で 1 桁変わります。比べるときは、キャッシュなしの費用を使います
- 比べる条件は、一度に 1 か所だけ変えます。実験の途中で条件を足すときは（実装の K=3、発展の v2・v3）、足した理由と予測を、実行する前に書きます
- 集計の数字が予測や取得の数と合わないときは、表を解釈する前に、回答の本文と数え方のコードを読みます（今回は 3 回、数え方の誤りが見つかりました）
